# Domain Dev Environment

Builds `devenv/` in the knowledge-base root: one Docker Compose environment that runs the domain's services together on shared infrastructure, any of them from a developer's own branch or worktree with live reload and a debugger, or one of them alone with its peers mocked. It reads the repos, proposes a manifest a person reviews, applies the person's answers, renders the environment from it, and proves it starts. It never changes a service repository.

## When to Use

- A cross-service flow must be verified locally, by hand or with Playwright, with some services running a developer's unmerged work
- A new domain needs its environment (`init`, then `decide` with the answers to its unknowns, or `render` when it has none), the repos changed what they need (`update`, `update --check`), or the seeded stubs need bodies (`stubs`)

**Not for:** performance or load testing (one shared instance per engine, development settings); production parity of instance settings; repos outside `repos/`, which a person adds there first.

## Inputs

| Input       | Required | Notes                                                                                                               |
| ----------- | -------- | ------------------------------------------------------------------------------------------------------------------- |
| Mode        | no       | `init` (discover, write the manifest, stop for review), `render` (manifest to files, verify), `update` (rediscover, propose manifest changes, render), `decide` (apply a person's answers, render), `stubs [<peer or external> ...]` (fill seeded stub bodies). Omitted: `init` when `devenv/devenv.yaml` is absent, else `update --check`; the Mode line says `(inferred)` |
| Answers     | `decide` | The person's answers in chat ("pin redis 7.4", "drop kafka", "use realm sso with users a and b"); none given, `decide` stops (Step 2) |
| `--check`   | no       | With `update` or `decide`: report the proposed changes and write nothing                                             |
| `--flow <name>` | no   | The manifest flow verification starts; default the smallest flow other than `all` that keeps a rendered member (the first in manifest order on a tie), else `all` |
| `--no-up`   | no       | Verify the configuration only; start nothing                                                                         |
| `--keep`    | no       | Leave the verified stack running                                                                                     |

Steps per mode: `init` 1-4 and 9; `update` 1-4 and 7-9; `decide` 1, 2, 5, and 7-9; `render` 1, 2, and 7-9; `stubs` 1, 2, 6, and 9.

## Workflow

### Step 1 - Behavioral Principles

Use skill: `behavioral-principles`.

### Step 2 - Locate the root and check the mode

Use skill: `domain-devenv-layout` for every path, field, template, and host rule named below, Use skill: `domain-devenv-stack-profiles` for the profile lines Step 4 reads and the slots Step 7 renders, and Use skill: `domain-kb-layout` for its Rules and the `_index/sync-state.json`, `_index/priority.json`, and flow card entries. The root is the working directory. No `repos/` directory, or one with no subdirectory, stops with `no repos - add the service repos under repos/ first`. `init` with `devenv/devenv.yaml` present stops with `devenv exists - run task-domain-devenv update`; any other mode without it stops with `no manifest - run task-domain-devenv init`; `decide` with no answers stops, after those and before the `--flow` check, with `no answers - run task-domain-devenv decide with your answers`. The knowledge base counts as synced when `sync-state.json` records a `sha` for any repo; only then are `surfaces/<repo>.md`, flow cards, and `priority.json` read (a listed file that is absent is read as absent), a non-null `in_progress` there puts the Sync line on the console, and each repo whose checkout `HEAD` differs from its recorded `sha` goes on the Drift line; unsynced, neither line, whatever `in_progress` holds. While `in_progress` names `init` or `update`, every `task-domain-sync` remedy this workflow emits reads `task-domain-sync --resume`; when it names `import` the remedy keeps its plain form (the knowledge-base layout's blanket `--resume` rule read with this one exception), since `--resume` only clears an interrupted import and itself says to re-run it, which the Sync line's own remedy covers. `render`, `update`, `decide`, and `stubs` without `--check` check `docker info` once (under `--no-up` too, for `caddy adapt`); unreachable, verification runs config-only, `stubs` fills nothing, and the Verify line says why. In every mode but `init`, a typed `--flow` that the manifest's `flows` lacks stops with `unknown flow <name> - flows: <keys>`. A stop emits its message alone, no console block. Every repo is read at its checkout `HEAD`, whatever `sync-state.json` records.

Harness guards may refuse a read of an env-like file, or any command whose text names one (`sources.env`, a manifest path such as `uses.x.env.KEY`): manifest edits and checks run as script files, never inline, and a refused read is reported, never worked around. Scratch (inventories, helper scripts, downloads) goes under the root's `tmp/devenv/` (in the knowledge base's `.gitignore` once a sync scaffolded it); a check's container or network is removed before the report, and the verified stack stays up only under `--keep`.

### Step 3 - Discover each repo (`init`, `update`)

One subagent per directory under `repos/`, run in parallel (one after another when subagents are unavailable). The brief, whole: load `behavioral-principles`; load `stack-detect` (`Use skill: stack-detect`) on `repos/<repo>/` (its marker and instruction files, not the root's; detected afresh for this repo, since the root has no stack of its own and the result is per repo); load `domain-devenv-discovery` with that block, the other repo names, and, when synced, the paths of every `surfaces/*.md` (its own first; the others' `internal api` rows tell a peer and seed its stubs) and the `include=` part of the repo's `scope` (`all` as `all`; a `tables=` part stays with the knowledge base); read only - nothing under `repos/` is written and no command changes a repository's state; a file a guard refuses is listed, never worked around; write the inventory block alone to `tmp/devenv/<repo>.md` and reply with that path. The workflow reads the files back. The stack block is surfaced only through the inventory's `Stack` line, the manifest's `profile`, and the console table's `Stack` column.

The profile each inventory names is read from `domain-devenv-stack-profiles` (loaded at Step 2). A repo whose inventory reads `not a service` goes into the Services line's `excluded` list and appears nowhere else. Then re-file: an `External` row whose `Unknowns` line names candidate repos becomes a `Peer` row of the repo whose `Dev hosts` line serves that host (its calls kept), and the unknown is dropped; no match, it stays external. Each inventory's `Committed credentials` entries go to the Security line.

### Step 4 - Assemble the manifest (`init`, `update`)

Build the manifest from the inventories, every field the layout's Manifest section defines, in its order. A row marked ` (out of scope)` contributes nothing, and the service gets the line `<uses.<engine>, external.<name>, or processes.<name>>: used by out-of-scope code only, left out - add it back in devenv.yaml` for an engine, external, or process it alone carried.

- **Root:** `domain` is the root directory name, kebab-cased, a trailing `-kb` dropped (`update` keeps the manifest's); `proxy_port` 8000; `tls` at `init` is `issuer: mkcert`, `port: 443` whatever the repos say, and `update` keeps the manifest's `tls` (a person's `issuer: none` or other port stands) - every host and origin below is computed from the `tls` in force; `decisions` `{}` at `init`, kept on `update`.
- **Infra:** one entry per engine some `Uses` row names, `sqlite` excepted (it needs none). An engine's `image` is its repository (`mysql`, `postgres`, `redis`, `rabbitmq` with a `-management` tag, `apache/kafka`, `quay.io/keycloak/keycloak`) at the one exact version the inventories' `Engine` rows name, decided in this order: any row reading `unknown - Keycloak below 26`, `unknown - Kafka below 3.7 (apache/kafka image floor)`, or `unknown - kafka image <image>` makes the entry that value; else several exact versions `unknown - versions differ: <version> (<repo>), ...`; else the one exact version, other `unknown` rows ignored; else a row's `unknown - floating tag <tag>`; else `unknown - no production version in the repos`; `evidence` is the row cited. `host_port` is the engine's own port for `mysql`, `postgres`, `redis`, and `rabbitmq`; `keycloak`, `kafka`, and `mailpit` take none. `rabbitmq.vhost` is `domain`; `topology` is `provisioned` when any inventory's Topology line says so, with the union of their declarations as `declarations`, else `apps`. `keycloak.realm` is the realm a `(hardcoded)` row names (two different: `unknown - realms differ: <realm> (<repo>), ...`), else `domain`; `host` by the layout's host rule from the `Dev hosts` `keycloak` lines and `(hardcoded)` host rows, the other named hosts as `host_aliases`; `users` one per distinct role in the union of every `uses.keycloak.roles`, username and role the same, else one `dev` user with no roles. Tool images - `mailpit` (`axllent/mailpit`, when any inventory uses it; it has no `Engine` row), `wiremock` (`wiremock/wiremock`), `proxy` (`caddy`, on Docker Hub `library/caddy`), `playwright` (`mcr.microsoft.com/playwright`, when a frontend exists), `curl` (`curlimages/curl`, with `topology: provisioned`) - are the newest tag of the accepted shape the registry's tag list returns (`https://hub.docker.com/v2/repositories/<repo>/tags?page_size=100`, `https://mcr.microsoft.com/v2/playwright/tags/list`; shapes: `X.Y.Z` for wiremock, caddy, and curl, `vX.Y.Z` for mailpit, `vX.Y.Z-noble` for playwright, newest by numeric X, Y, Z, every other tag skipped), else `unknown - pin a tag`; `update` keeps a pinned one and looks an `unknown - pin a tag` one up again. A tag list is saved to a file in a new directory under `tmp/devenv/` and parsed by a script kept outside it with an isolated interpreter (`python3 -I`, or `python -I` where that is the name), never piped into one; the Hub list is ordered by update time, not version, so it is filtered to the shape before the numeric sort, and a lookup for one minor adds `&name=<minor>.`. An engine minor a person pins (Step 5) resolves on the same lists, every lookup keeping only tags that start with the typed value and a `.`: Docker Hub `library/<engine>` for mysql, redis, and rabbitmq (`X.Y.Z`, rabbitmq `X.Y.Z-management`), postgres (`X.Y`), and `apache/kafka` (`X.Y.Z`); `https://quay.io/api/v1/repository/keycloak/keycloak/tag/?limit=100&onlyActiveTags=true&filter_tag_name=like:<minor>.` for keycloak (`X.Y.Z`).
- **External:** `external.<name>` per distinct `External` row (rows matched across repos by host, as discovery matches them; the name the first inventory in `repos/` order gives), kebab-cased, with its `port` (`unknown - <why>` kept, which keeps every service using it out of the render; rows naming different ports `unknown - ports differ: <port> (<repo>), ...`) and the union of its `calls`, a `none - ...` cell contributing nothing (an empty list seeds no stub). An external with a ` (browser)` key gets `routes` at the dev value's path on a host chosen like the Keycloak host with `<name>` for `keycloak` (a `mock` dev host naming it first); one with a ` (host only)` key gets `tls: true`, its paired scheme key `https`.
- **Services:** one entry per inventory, keyed by the repo directory name, in `repos/` order; every inventory value is taken without its ` - file:line` citation, which goes to `evidence`. `profile` and `kind` from their lines; `runtime` from the Stack line's version; `port` the inventory's (a `profile default` is written as the number); `host_port` from 3001 in manifest order; `debug_port` from 12341 in manifest order among the services whose profile `Debug port` line names one, absent for the others; a `worker` omits `port`, `host_port`, `health`, and `routes`. `packages` is each `Packages` entry's package name alone (its `(because ...)` part is not recorded; the citation goes to `evidence`); `processes` the Process table (`default` kept, `{run, live}` and `{live}` forms kept, a `Port` added as `port`); `migrate` (its `; definer - file:line` suffix dropped, read by `grants` below), `health`, `build` (with `secrets`, `ssh`, `node`, `framework_version`; a `none` list value leaves its key out, a scalar `none` such as `debugger` or `generate` is written), and the profile fields (`module`, `main`, `tools`) from their lines, `unknown` values kept and a `none - <evidence>` value written `none`. `env` is the Env table plus a `sqlite` row's key and Dev value (never under `uses`), a ` (self origin)`, ` (self host)`, or ` (self port)` key set to the service's first route origin, its host, or the port that origin uses (`tls.port`, `proxy_port` with TLS off; no route: the key is `unknown - no route to build the self origin from - set routes`, with the line `env.<KEY>: no route - set routes`); `secrets` the Secret table. Every value built from a route, a port, or the `tls` in force (self keys, host-only keys, peer keys, SAML `entity_id` and `acs`), outside a `decisions` path, is recomputed on `update` and on `decide` from the manifest's `routes`, `port` values, `tls`, and the `(path ...)` an unknown keeps, as they stand, so the route, port, or `tls` a person sets resolves its `unknown`; such a resolution, or a recomputed value that now differs from the manifest's, is applied without asking and listed as an applied proposal with `recomputed` as its evidence, never kept as a person's edit. `uses.<engine>` carries `database` (the `database` role's Dev value, or the one inside a `url` role's value, else `<user>_development`; each other database its rows name in `databases`; `create: false` when the profile's `Database create` line reads `false - ...` (the layout's slot rule derives the same value from that line); on mysql `grants` when the Migrate line notes a definer - `[SUPER]` below MySQL 8.0.22, `[SET_USER_ID]` from 8.0.22 below 8.2, `[SET_ANY_DEFINER, ALLOW_NONEXISTENT_DEFINER]` from 8.2; with the image `unknown`, `grants: unknown - mysql version unknown` and the line `uses.mysql.grants: mysql version unknown - pin infra.mysql.image`), `db` for redis (from 0, in manifest order; a seventeenth reads `unknown - more than 16 redis users`, with the line `uses.redis.db: more than 16 redis users - set db or add another redis by hand`), `client` (the `client id` Dev value, else the service key), `roles` (the inventory's `Roles` line; a `Roles` line on a service with no keycloak row is an unknown, `uses.keycloak.roles: <roles> checked but no OIDC key - set uses.keycloak`), and from a `SAML` line `protocol: saml` with `entity_id` and `acs` its first route's origin plus those paths (no route: `entity_id` and `acs` read `unknown - no route to build the SP origin from (path <that path>) - set routes`, with the lines `uses.keycloak.entity_id: no route - set routes` and `uses.keycloak.acs: no route - set routes`; a pinned IdP certificate adds the label line `idp signing key: pinned at <where> - a person sets a fixed signing key in local/keycloak-realm.json`) for keycloak, and under `env` every config key of the engine with the naming contract's value for its `Role` (a `url` keeps its Dev value's scheme and driver prefix; `issuer` is `<keycloak origin>/realms/<realm>`; `base url` the Keycloak origin; a keycloak `url` is the Keycloak origin plus the Dev value's path; `other` keeps the Dev value; a `(hardcoded)` row sets no key). `peers.<peer>` carries `calls` (a ` (matched, unconfirmed)` suffix kept in the quoted string; Step 7 strips it for the stub and notes it there) and, under `env`, each key with its marker stripped from the name, valued by the peer-key table below. `external.<name>.env` keys are `http://<name>.mock:<port>` plus the path of the Dev value (an external whose `port` is `unknown - ...` makes the key `unknown - external <name> port unknown (path <the Dev value's path, or none>)`, with the line `external.<name>.env.<KEY>: external port unknown - set external.<name>.port`; `https://<name>.mock` plus it with `tls: true`, a ` (host only)` key `<name>.mock`, a ` (browser)` key the origin of its route host plus the path); an address that is not a URL (a bucket, queue, or resource name) keeps its value and adds the label line `not-a-url <name>.<KEY>: not a URL - set external.<name> and the key by hand`. An `Edge headers` entry from a cookie becomes `headers` on each of the service's routes; another source is the label line `edge-header <Header>: from <source> - set it in local/caddy`. `evidence` maps every cited slot (`runtime`, `port`, `health`, `migrate`, each `packages`, `build`, process, config key, peer, and external entry) to its `file:line`; `unknowns` is the inventory's `Unknowns` lines, verbatim (`[]` for `- none`), except that a line whose field path holds a value while its problem stands (`uses.keycloak.roles: client scope ...`, `uses.keycloak.roles: roles live in the database ...`, `build.secrets: <KEY> needed by the live install ...`) takes a label slot instead (`client-scope <x>:`, `db-roles:`, `live-install-secret <KEY>:`), plus the lines this step adds.
- **Routes:** a service with a `Dev hosts` `route` line gets `host` that name, `path` `/`; a backend some service calls through a ` (browser)` key gets a route on the caller's route host (a caller with none: the peer's own host, as for a pathless value) at the path of the key's Dev value when the value has a path and its host is the caller's host, `localhost`, or a loopback address, on the value's host at that path when the host is another, and `/` on its own host (its dev host, else `<svc>.localhost`) when the value has no path; a frontend, or a backend some service calls through a ` (browser)` key, with no dev host is routed `/` at `<svc>.localhost`; a process with a `port` gets a route with `process` on the service's route host at each path its row names; the peer-key table adds the routes its last column names. A `mock` dev host is never a route. One `/` route per host: two services claiming `/` on one host get `routes: unknown - host <h> also claimed by <svc> - set routes` in place of their routes, each with the line `routes: host <h> also claimed by <svc> - set routes`, which keeps both out of the render; a backend's path route under its caller's host is no claim.
- **Flows:** `all` with every service, in manifest order; when synced, each card (the `priority.json` entries in their order, then the cards it does not list in path order) whose `freshness` is not `orphaned` and whose `files` list names two or more manifest services (the segment after `repos/`, segments that are not a service key dropped), as `<capability>/<flow>: [those services, in manifest order]`, at most eight besides `all`; unsynced, `all` only and the Informational line (the manifest has no slot for it) `flows: all only - the knowledge base is not synced - name the flows in devenv.yaml, or run task-domain-sync init (task-domain-sync --resume when sync-state.json records an in_progress value)`, dropped once `flows` holds more than `all`.

A peer is proxied for a key when the key's Dev value is `https://` or the peer has constrained `Route hosts` or forces HTTPS, else direct. The peer host is the Dev value's host when it is one of the peer's dev, constrained, or route hosts, else the peer's first constrained host, else its first `route` dev host, else the host of its `/` route, else `<peer>.localhost`; the peer origin is the origin the layout's host rule yields for the peer host under the `tls` in force, and the proxied host is the peer origin's host. On `decide`, with no inventory, the proxied test and the peer host are read from the key's current value (direct when it starts `http://<peer>:` or `<peer>:`; proxied when it carries a host the layout proxied before this run's answers) or from its unknown (a `path <p>` element marks a direct form, a `host <h>` element a proxied one); a value with neither, and no unknown form, is kept as it stands. A direct form on a peer whose `port` is `unknown - ...` reads `unknown - peer <peer> port unknown (<url | host:port>, path <the Dev value's path, or none>)` (`url` covering `-`), with the line `peers.<peer>.env.<KEY>: peer port unknown - set services.<peer>.port`. A route the table adds is not added twice, and a `/` it would add to a host that already carries any service's `/` is not added: when the peer then has no route on that host whose path covers every `calls` path of this caller, the key reads `unknown - host <h> serves <svc> at / (<url | host:port | host only>, host <h>) - set routes` (`url` covering `-`), with the line `peers.<peer>.env.<KEY>: host <h> serves <svc> at / - set routes`.

The manifest is written by the layout's emission rule (header comment, double-quoted strings), parsed back with any available YAML parser, and checked: unique ports, every flow member a service key, every service value starting `unknown` backed by an `unknowns` line of that service (an infra, external, or tool-image `unknown - <why>` carries its reason itself); a failure is fixed before the step ends. `init` writes `devenv/devenv.yaml` and goes to Step 9. `update` compares the assembled manifest with the existing one and lists each difference as a proposal, of these kinds only (plus the recompute rule's applied proposals): a service added (a directory under `repos/` the manifest lacks whose inventory is a service) or removed (a manifest service whose directory is gone, whatever the knowledge base lists; flows drop it); an infra entry, external, config key, process, peer, route, secret, role, package, build key, or `unknowns` line (one whose slot no manifest line covers) added or gone; a value whose evidence changed (the manifest's `evidence` entry names another file, or its `file:line` now states another value - a line that moved with the same value is not a change, and `update` refreshes the line number silently); a flow whose card-derived member list changed (`all` follows the services); a route host, the Keycloak `host` or a `host_aliases` entry, an external's route host, or an env value carrying a proxied host or origin (a bare host included) that the `tls` in force and the host rule no longer yield (rewritten in place, as the layout says, and listed as an applied proposal). A field at or under a `decisions` path is never proposed, whatever its evidence says, nor is a service's `uses` or `external` entry for an infra entry or external a `decisions` entry removed. An `unknowns` line whose field-path slot now holds a value not starting `unknown`, or whose slot a `decisions` path covers, is dropped silently; a `verify` label line (Step 8's) is neither assembled nor proposed gone, Step 8 rewrites them. Any other difference is a person's edit, kept and never proposed; a field with no `evidence` entry (`domain`, `proxy_port`, `tls`, a pinned tool image, a `host_port`, a `debug_port`, a `tools` pin, a hand-written unknown, and a route, process, peer, secret, or `uses` entry a person added) keeps the manifest's value and is proposed only when its whole entry is added or removed (a whole entry reads `none -> <entry>` or `<entry> -> none`); a tool image still `unknown - pin a tag` takes the lookup's result. A manifest whose `evidence` maps are empty (hand-written, or from an earlier version) has nothing to compare evidence against: every value difference, an infra entry's included, is then a proposal. The console then describes the manifest as it stands (its services, flows, and the table; a removed service's `Stack` reads `-`) and the proposals describe the change; a violation Step 7 would report in the existing manifest, or an existing `unknown` value no line backs, is a Blocking line `manifest: <field> - <violation> - fix devenv.yaml` and never stops `update`. With `--check` the workflow goes to Step 9 with the list (`unchanged` when it is empty). Otherwise, with no proposals it reports `unchanged`, writes the silent changes (refreshed lines, dropped lines) without asking, and continues; with none still to accept it writes the applied proposals and the silent changes without asking and continues; with some still to accept it asks once with the full list, applies the accepted proposals, writes the manifest, and continues only once answered.

### Step 5 - Apply decisions (`decide`)

Each answer becomes one edit, listed as a proposal with `decision` as its evidence: a value set (a `tls`, `proxy_port`, `routes`, or `port` answer also recomputes every value built from them (Step 4's recompute rule), a `tls` or `proxy_port` answer rewriting every host and origin by the layout's host rule as Step 4's `update` does; a pinned mysql image also sets `grants`, on each mysql service that has the key, by Step 4's rule); an entry added or removed (a removed infra entry or external also leaves every service's `uses` or `external`, and those services' lines about it go); an engine minor (`7.4`) resolved to the newest exact patch tag by Step 4's registry lookup (its engine lists and shapes; a minor below an engine floor, Keycloak 26 or Kafka 3.7, is refused with Step 4's `unknown - ... below ...` reason and asked back); a task added. Each edit adds `<field path>: <today> - <the person's reason, else their words>` to `decisions`, and every `unknowns` line it resolves is dropped. An answer no field can carry is asked back once. A repo change the person accepts becomes a patch proposal, never applied: `local/patches/<svc>-<slug>.patch`, minimal, keeping the current value as the fallback (an env read with today's value as the default), with the manifest pre-wired for it (the env key, the IdP client), so applying it in a worktree is the only step left. The manifest is then emitted and checked as in Step 4. With `--check` the workflow goes to Step 9 with the list, the patch described in its proposal line and not written; otherwise it writes the manifest and each patch, checks the patch with `git -C repos/<svc> apply --check <absolute path of the patch>` (which writes nothing), and continues.

### Step 6 - Fill stubs (`stubs`)

Fills the seed stubs that still carry `metadata.todo` (a person's edited stub is kept), for the named peers and externals, else all, reading `repos/` and writing only those stub files. A body comes from the first source that has one: the repos' own mock-server mappings in their dev setup (the `Host` matcher rewritten to the layout's, response files inlined); recorded HTTP fixtures; spec fake responses and factories; last, the client's response parser, `metadata.source` `derived from <file:line>`. One file per call; several scenarios as `{"mappings": [...]}`, the success mapping first, each error scenario keyed to a sentinel input (a reserved id, an email prefix) named in its `metadata`; `metadata.source` names the origin and `metadata.todo` is removed; credentials, tokens, and account numbers are masked; only calls the repo's `scope` covers. Calls sharing one path are told apart by what distinguishes them (an operation header, a body field, a query marker such as `?uploads`, the content type); a binary body is `base64Body`. With Docker unreachable or the wiremock image `unknown`, no stub is filled and Verify says which. Validation: a throwaway container on the manifest's wiremock image per stub folder with that mock's own command (the peer mocks' `--global-response-templating`, the external mocks' `--port`; under Git Bash `MSYS_NO_PATHCONV=1` and `$(pwd -W 2>/dev/null || pwd)` on the mounts), each mapping requested with its `Host` and answering its status, a wrong `Host` answering 404, then the container removed; a stub that fails (a body the response templating misreads answers 500) is fixed, else restored to its seed and named on the Verify line.

### Step 7 - Render (`render`, `update`, `decide`)

Validate the manifest's structure: unique `host_port`, debug, `proxy_port`, and `tls.port` values, one `/` route per host, every flow member a service key, no `latest` or tag-less image, every value inside its enum, and the layout's TLS-off host rule. Invalid, the workflow writes nothing and goes to Step 9 with `Verify: config invalid - <first violation>`. An `unknown` value is never a violation: a service with one at any depth under a field rendering reads (the layout's rule: `routes`, `uses`, `env`, `peers`, and `external` included), lacking a field its profile needs, using an infra entry or external with one, using an external with `tls: true` or a `hijack` list while `tls.issuer` is `none` or `tls.port` is not 443 (the layout's container-only host rule; listed as `<svc> - external.<name>: tls: true or hijack needs TLS on at 443`), or depending on an unpinned tool image (`proxy`: every service; `wiremock`: every service with peers or externals; `curl`: every service using rabbitmq with `topology: provisioned`; `playwright`: `e2e`, listed under `Not rendered` by that name) is left out of every rendered file and listed under `Not rendered`; flows drop it. Write every `regenerate` file from the templates with each profile slot from `domain-devenv-stack-profiles` (loaded at Step 2), the `local/` inclusions the layout names, `chmod +x devenv/bin/dev` after writing it (when `git config core.fileMode` reads `false`, or the file is tracked without mode `100755`, the Files line ends `; bin/dev: git add --chmod=+x devenv/bin/dev before committing`); delete the `regenerate` files of a service that is no longer in the manifest or is not rendered (its overlays, `services/<svc>/`, `.devcontainer/<svc>/`), counted as removed; a file or folder the layout's folder table does not list (a person's `NOTES.md`) is left alone. Write every `seed` file only when absent: a peer stub is `stubs/peers/<peer>/<method>-<path>.json` and an external stub `stubs/external/<name>/<method>-<path>.json`, method lower-cased, the leading `/` dropped, each other `/` written `-`, `{param}` written `param`, a bare `/` written `root`, a `:` or `*` written `-` (`POST /payments/refunds` is `post-payments-refunds.json`, `GET /payments/refunds/{id}` is `get-payments-refunds-id.json`; two calls mapping to one name take `-2`, `-3` suffixes in `calls` order); an SDK operation call (`PutObject`, `SendMessage`) is `stubs/external/<name>/<operation lower-cased>.json`, its mapping keeping the `Host` matcher, setting `method` and a `urlPathPattern`, and telling the operation apart by the Step 6 marks (an operation header such as `X-Amz-Target`, a body field such as `Action=<Op>`, a query marker such as `?uploads`, the content type); each stub carries `metadata.evidence`, the `evidence` entry of the first service in manifest order that names that peer or external, the key dropped when there is none, and, for a `calls` entry carrying ` (matched, unconfirmed)`, the suffix stripped from the file name and `urlPath` and `metadata.note: matched by name, unconfirmed` written; `seed files kept` counts the seed files the manifest implies that already existed. `sources.env` and anything under `.cache/`, `wt/`, `local/`, or `infra/tls/` are never written by the workflow (`bin/dev` or a person owns them; the render seeds only the `local/` `.gitkeep` files, and `decide` alone adds patches under `local/patches/`), nor anything outside `devenv/` and `tmp/devenv/`; `devenv.yaml` is written only in Steps 4 and 5 and by Step 8's unknowns.

### Step 8 - Verify (`render`, `update`, `decide`)

Run `bash -n devenv/bin/dev`, then, in `devenv/`, `docker compose -f compose.yaml -f compose.local.yaml --profile '*' config -q` and the same with `-f overlays/<svc>.live.yaml` inserted before `compose.local.yaml` for each rendered service and with `-f overlays/<svc>.solo.yaml` so inserted for each (explicit `-f`, so the `COMPOSE_FILE` a previous `bin/dev up` left in `.env` is not read); with Docker reachable and the proxy image pinned, `MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W 2>/dev/null || pwd)/infra/caddy/Caddyfile:/etc/caddy/Caddyfile:ro" -v "$(pwd -W 2>/dev/null || pwd)/local/caddy:/etc/caddy/local:ro" <proxy image> caddy adapt --config /etc/caddy/Caddyfile` checks the Caddyfile and its `local/` imports (no certificate needed; no other mount, so Docker creates no `infra/tls/`). A failure is a rendering defect: it ends the step with `config invalid - <first error>` when the fix below does not clear it. Unless `--no-up`, Docker is unreachable, nothing is rendered, the flow has no rendered member, the Compose project is already running (`docker compose ls` lists `<domain>`; Verify then reads `not started - stack already running`), or `tls.issuer` is not `none` and `infra/tls/cert.pem` is absent (the workflow never runs `bin/dev certs`, which creates a CA on the developer's machine), run `bin/dev up <flow>` with the developer's `sources.env` as it stands (`bin/dev` creates it from the example when absent, so unmapped services run pinned from `repos/`), and read each service's state from `docker compose ps -a` (a `worker` has no healthcheck: `running` is its healthy state). A failing service's last 40 log lines classify the cause: a rendering defect (a wrong command, path, package, port, or escape) is a slot filled wrongly, fixed in the render and the step repeats, at most twice; a cause in the service (a missing secret, a failed migration, a hardcoded host) is appended to the service's `unknowns` in the manifest and reported, written as the label line `verify <svc>: <cause> - <what to set>`, a missing secret's ending `- set it in devenv/sources.env`; the `verify` lines are rewritten whole each time this step runs (none left when it does not start the stack), and a repeat after a render fix counts as the same start, so the already-running guard does not fire on it. Then, when this step started the stack, `bin/dev down` unless `--keep`.

### Step 9 - Report

Emit the console block. An unknown is blocking when it keeps a service out of the render or out of a healthy start: every `unknown` infra and external value, every service field whose value starts `unknown` (at any depth), each service Step 7 left out for a `tls: true` or `hijack` external (`- {svc}: external.{name} - tls: true or hijack needs TLS on at 443 - set tls`) or for a field its profile needs (`- {svc}: {field} - required by the {profile} profile - set it`), each `verify` line the manifest holds (Step 8 rewrites them when it runs), and the manifest lines of Step 4, as `- {svc or infra or external or manifest}: {field} - {why} - {what to set}` (an `unknown - <why>` value `- {owner}: {field} - {why} - set it in devenv.yaml`), ordered by the number of services each keeps out, most first, then by field path. Blocking describes the manifest as this run leaves it (under `--check`, as it stands). Every other `unknowns` line is informational: the console counts them per service, a line a Blocking entry shows not counted, and the manifest and README hold them in full. `Infra` lists the engines only, as does the table's `Uses`; `hosts` is the layout's proxied hosts. Excluded repos appear only in the Services line.

## Avoid

- Editing, committing, or adding files to a service repository (a `decide` patch is written under `devenv/local/patches/`, never applied), or using its existing Dockerfile or compose file as the template
- Pointing live mode or a bind mount at `repos/<svc>`
- Hand-editing a generated file to make verification pass instead of fixing the render
- Choosing between two production versions of one engine without asking
- Reusing a repository's TLS certificate or key, or running `mkcert` on the developer's behalf; a committed development IdP signing key enters `local/keycloak-realm.json` only by a person's decision
- Retrying a guarded read through another command, spelling, or tool
- Reaching for a cloud-service emulator image when stubs cover the calls the in-scope code makes

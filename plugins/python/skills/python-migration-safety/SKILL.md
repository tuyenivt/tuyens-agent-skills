# Migration Safety

> Load `Use skill: stack-detect` first to determine the project stack.

## When to Use

- Creating or reviewing Alembic (FastAPI/SQLAlchemy) or Django migrations
- Planning zero-downtime schema changes under rolling deploys
- Adding enums, indexes, or constraints to existing tables
- Recovering a migration that failed or partially applied in production

## Rules

- Review every autogenerated migration: it misses renames (drop + add), CHECK constraints, enum values, custom types
- `SET LOCAL lock_timeout = '2s'` before every `ACCESS EXCLUSIVE` statement, with Alembic `transaction_per_migration=True` in `env.py` (by default all pending revisions share one transaction and even `SET LOCAL` carries over); `CONCURRENTLY` builds `SET lock_timeout = 0` in `autocommit_block` - a timeout leaves an `INVALID` index
- Patterns assume PostgreSQL 12+; another `Database:` keeps only the engine-neutral rules (expand-contract, separate data revisions, deploy order, up/down/up CI), stated in the plan; `unknown` means PostgreSQL `(assumed)`
- Data migrations get their own revision, never mixed with schema changes
- NOT NULL with a constant default is one step (PG 11+ metadata-only); a per-row value is added nullable, backfilled, `CHECK ... NOT VALID`, `VALIDATE`, then `SET NOT NULL`
- `CONCURRENTLY` cannot run inside a transaction block: Alembic `with op.get_context().autocommit_block():`, Django `atomic = False` + `AddIndexConcurrently`
- Never rename a column in one deploy - expand-contract (Column Rename pattern)
- Multi-step patterns deploy across releases, not one; a migration already applied anywhere is superseded by a new revision, never edited - one that failed before being recorded is rewritten in place
- Additive changes (columns, indexes) migrate before the code that uses them; drops migrate after code stops referencing; a new enum value is written one release after it commits
- CI runs migrate up -> down -> up
- Test the downgrade (Alembic) or `reverse_sql` (Django) of every reversible step; a forward-only step states why in the Rollback Plan

## Patterns

### Alembic vs Django Operations

Alembic: `alembic revision --autogenerate -m "..."`, `alembic upgrade head`; Django: `manage.py makemigrations`, `manage.py migrate`.

### Add Column Safely

```python
# Alembic, schema only
def upgrade():
    op.execute(sa.text("SET LOCAL lock_timeout = '2s'"))
    op.add_column("orders", sa.Column("tracking_number", sa.String(100), nullable=True))
    op.add_column("orders", sa.Column("source", sa.String(20), nullable=False, server_default="web"))
```

### NOT NULL on Large Table (Per-Row Value)

Direct `SET NOT NULL` scans under `ACCESS EXCLUSIVE`. Four releases: (A) add nullable, dual-write; (B) backfill; (C) `NOT VALID` + `VALIDATE`; (D) `SET NOT NULL`, drop the CHECK:

```python
# Step 1 (release A): add nullable column
op.execute(sa.text("SET LOCAL lock_timeout = '2s'"))
op.add_column("orders", sa.Column("shipping_address", sa.String(500), nullable=True))

# Step 2 (release B, data revision): keyset batches, one transaction each
conn = op.get_bind()
with op.get_context().autocommit_block():
    last_id = 0
    while True:
        res = conn.execute(sa.text("""
            UPDATE orders SET shipping_address = 'UNKNOWN'
            WHERE id IN (SELECT id FROM orders WHERE shipping_address IS NULL AND id > :last_id
                         ORDER BY id LIMIT 1000) RETURNING id"""), {"last_id": last_id})
        ids = [r[0] for r in res]
        if not ids: break
        last_id = max(ids)

# Step 3 (release C): NOT VALID - brief ACCESS EXCLUSIVE, no scan
op.execute(sa.text("SET LOCAL lock_timeout = '2s'"))
op.execute(sa.text("ALTER TABLE orders ADD CONSTRAINT orders_shipping_nn CHECK (shipping_address IS NOT NULL) NOT VALID"))
# Step 4 (release C, own revision - inside Step 3's it scans under ACCESS EXCLUSIVE): ShareUpdateExclusiveLock only
op.execute(sa.text("ALTER TABLE orders VALIDATE CONSTRAINT orders_shipping_nn"))

# Step 5 (release D): PG 12+ proves NOT NULL from the validated CHECK, no scan; then drop the CHECK
op.execute(sa.text("SET LOCAL lock_timeout = '2s'"))
op.execute(sa.text("ALTER TABLE orders ALTER COLUMN shipping_address SET NOT NULL"))
op.execute(sa.text("ALTER TABLE orders DROP CONSTRAINT orders_shipping_nn"))
```

Django (each schema migration atomic, opening with `RunSQL("SET LOCAL lock_timeout = '2s'")`): `AddField(null=True)`; `RunPython` on an `atomic = False` migration saving `apps.get_model(...)` rows in `transaction.atomic()` batches of 1000; `AddConstraintNotValid`, then `ValidateConstraint` in its own migration; `AlterField(null=False)` on a field with no `default`/`db_default` (a default makes Django `UPDATE ... WHERE col IS NULL` first) + `RemoveConstraint`.

### CREATE INDEX CONCURRENTLY

```python
# Alembic - a failed build leaves an INVALID index; drop it before retrying
with op.get_context().autocommit_block():
    op.execute(sa.text("SET lock_timeout = 0"))  # plain SET under autocommit
    op.execute(sa.text("CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_orders_status ON orders (status)"))
    # composite: leftmost-prefix order matters
    op.execute(sa.text("CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_events_acct_created ON events (account_id, created_at)"))
    op.execute(sa.text("RESET lock_timeout"))  # else 0 outlives the block into later revisions

# Django - records the index in migration state; reverse is RemoveIndexConcurrently
from django.contrib.postgres.operations import AddIndexConcurrently

class Migration(migrations.Migration):
    atomic = False
    operations = [AddIndexConcurrently("order", models.Index(fields=["status"], name="ix_orders_status"))]
```

**Unique constraint on an existing table**: duplicates fail the build and leave an `INVALID` index. Resolve them first (batched data migration), `CREATE UNIQUE INDEX CONCURRENTLY`, then `ALTER TABLE t ADD CONSTRAINT c UNIQUE USING INDEX ix` - no rebuild; the index is renamed to `c`, so the reverse is `DROP CONSTRAINT c`. `USING INDEX` takes `ACCESS EXCLUSIVE`: Alembic runs it after the `autocommit_block`; Django splits it - an `atomic = False` migration with `RunSQL("CREATE UNIQUE INDEX CONCURRENTLY ix ...", reverse_sql="DROP INDEX CONCURRENTLY IF EXISTS ix")`, then an atomic one opening with `RunSQL("SET LOCAL lock_timeout = '2s'")` and `SeparateDatabaseAndState(database_operations=[RunSQL("ALTER TABLE t ADD CONSTRAINT c UNIQUE USING INDEX ix", reverse_sql="ALTER TABLE t DROP CONSTRAINT c")], state_operations=[AddConstraint(...)])`.

### Enum Changes (PostgreSQL)

Django `CharField(choices=...)` has **no DB enum type**: adding a value is a `choices`-only `AlterField` that emits no SQL; removing one needs a data migration moving rows off it first. Native PostgreSQL `ENUM`: `ADD VALUE IF NOT EXISTS 'refunded'` runs in-transaction (PG 12+) but is unusable until commit - never write it in the same revision; `RENAME VALUE 'old' TO 'new'` exists; removal is unsupported - new type, migrate the column, drop the old type.

### Column Rename (Expand-Contract)

(1) add nullable column, (2) write both, read old, (3) backfill, (4) verify, read new, (5) stop writing old, (6) drop. Backfilling before dual-write loses rows written between.

### Recovering a Failed or Partial Migration

1. Compare `alembic current` / `django_migrations` with `information_schema.columns`, `pg_index` (`indisvalid`), `pg_constraint`, `pg_enum`: which effects exist.
2. Unblock writes first: `ALTER COLUMN ... DROP NOT NULL`, `DROP INDEX CONCURRENTLY IF EXISTS` on an `INVALID` index.
3. Re-split the revision into the multi-release shape; make every statement idempotent (`IF NOT EXISTS`, `IF EXISTS`) so a re-run skips effects already present; `IF NOT EXISTS` treats an `INVALID` index as present - step 2 always drops it.
4. `alembic stamp <rev>` (Django `migrate --fake`) only when every effect is present; otherwise re-run the idempotent revision. Record the stamp in the Deploy Sequence.

## Output Format

When authoring, emit this block then the migration files. When reviewing, the consuming workflow owns the finding envelope (label, severity, `file:line`; invoked standalone, order `[Must]` first and label each finding `[Must]` when it risks incorrect behaviour, data loss, or a security hole, `[Recommend]` otherwise); emit this block as the target state and one finding per deviation from it. `Safe Order` is the release letter; a Rollback row is a clean reverse (`DROP COLUMN`, `DROP CONSTRAINT`, `DROP INDEX CONCURRENTLY IF EXISTS`) or forward-only with the reason (backfill, `ADD VALUE`, dropped data).


## Avoid

- `WHERE col IS NULL LIMIT N` backfill loops (re-scan the same rows; use keyset pagination)
- `CREATE INDEX` (non-concurrent) on large tables
